Two Ideas About State

A contrast of jotai-branch and atoms-alt — May 2026

Both libraries start from the same discomfort with Jotai: the feeling that atoms, as shipped, conflate two separate concerns. But they disagree sharply about which two concerns are being conflated, and so they arrive at completely different abstractions.

jotai-branch says the problem is isolation. Global state is always shared, always live, which makes draft editing, optimistic updates, and transactional commits needlessly complex. Its answer is a shadow store you can branch, mutate privately, and then collapse back.

atoms-alt says the problem is coupling. Atoms in Jotai carry both their identity and their side-effect policy — an atom that persists to localStorage is a different type of object than one that does not. Its answer is to make atoms pure keys and move all behavior into a composable handler chain at the store level.

These are orthogonal problems. You could implement either solution inside the other, or combine both. That is worth keeping in mind as you read.

jotai-branch

Shadow Store

The core idea

A branch is a proxy store layered transparently over the global Jotai store. Reads fall through to the base unless the atom has been locally overridden; writes land in a private mutation map and never touch the base. commit() flushes the map; discard() wipes it. React context makes the branch invisible to child components — the same useAtom call in <ProfileForm /> reads from whichever store the nearest provider supplies. 

const branch = useBranch();

// ProfileForm doesn't know it's in a draft.
// Cancel is one line.
<BranchProvider branch={branch}>
  <ProfileForm />
  <button onClick={branch.discard}>Cancel</button>
  <button onClick={branch.commit}>Save</button>
</BranchProvider>
Novel The specific combination of (1) a proxy store that satisfies Jotai's StoreApi exactly, so it can be passed to existing useAtom calls without modification, (2) live base-store merging — unoverridden atoms still react to background updates even inside a branch — and (3) nested branches where each layer only sees its own overrides plus those of its parent.

The live-merge detail

This is the subtlest and most practically useful aspect. Imagine a user is editing a form. In the background, a websocket pushes a real-time update to the server's view of their data. In standard React you would have to manually decide whether to clobber the form draft or ignore the update. With a branch, the answer is automatic: atoms the user has touched are shadowed and immune; atoms they have not touched pass through and stay live. No custom merge logic required.

Prior art

LibraryOverlapGap
Recoil Snapshots Recoil's Snapshot is the closest analogue: an immutable fork of atom state, traversable and diff-able. Snapshots are read-only. There is no write-commit-discard lifecycle, no live-merge with the base store, and no transparent context injection for existing components.
Immer produce(state, draft => { ... }) is a structural match: draft, mutate freely, get back an immutable result. Immer operates on plain objects, not atom graphs. It has no notion of a derived atom recalculating inside the draft context, and no React integration at the store level.
React Hook Form Solves exactly the "form draft with cancel" problem, and solves it well — with controlled re-renders, validation, and dirty tracking built in. Entirely form-specific. Does not touch global state atoms. If your form reads from non-form atoms (permissions, pricing rules derived from the draft profile), RHF cannot help.
Valtio snapshot() captures a point-in-time read of a proxy store. Read-only, non-reactive, no commit path back to the source.
MobX transactions runInAction batches mutations atomically. Transactions are not isolating — all reads still see the live global state. There is no private mutation buffer you can discard.
Covered elsewhere The individual building blocks are not new: proxy stores, draft state, and immutable snapshots all exist. What does not exist in this exact form is the assembly: a branch that satisfies Jotai's store interface, integrates with React context invisibly, and performs live-merge on uncommitted fields.

atoms-alt

Handler Stack

The core idea

An atom is nothing but a symbol, a name, and a pure default. It carries no side-effect policy of any kind. All behavior — persistence, validation, logging, rate-limiting, caching — lives in a handler stack that is compiled once when you create the store. Handlers intercept reads, writes, or both, and call next() to pass control down the chain. The base of every chain is a plain Map. 

// The atom never changes.
const counter = atom(0, 'counter');

// The environment dictates the effects.
const store = createStore([
  HistoryHandler,
  new ValidatorHandler(),
  LocalStorageHandler,
]);
In Jotai, to persist and validate an atom, you write atomWithValidate(atomWithStorage('key', 0)). The atom's identity is now tangled with its environment. Swap environments — say, from browser to a test runner — and you must change the atom. — from atoms-alt.md
Novel The claim that both read and write can be intercepted in the same composable unit, applied globally to every atom in the store, with no per-atom registration. A LocalStorageHandler that caches reads and persists writes is ten lines of code and automatically covers every atom you ever define, including ones you add later.

The read-intercept complication

The read side of the handler is where the architecture meets its sharpest constraint: React. useSyncExternalStore calls getSnapshot — which becomes store.read — during the render phase. Any setState triggered synchronously from inside a read handler, even deferred to a microtask, causes an infinite render loop. This is not a fixable bug; it is a structural consequence of the architecture.

The correct pattern is to accumulate reads in a plain variable and flush them to React state only on the next write event, which always originates from user interaction and therefore always runs outside render. The read intercept is fully functional for non-React use cases — cache warming, analytics, server-side rendering — but requires care in a live React component tree.

Tension The handler stack's elegance in non-React code is real. Inside React, the read path is a second-class citizen. A library shipping this model would need to either document this prominently or build a convention (such as flagging which handlers are "render-safe") to prevent users from hitting the infinite loop.

Prior art

LibraryOverlapGap
Redux middleware The onion/chain composition model is identical. Middleware wraps dispatch, calls next, can short-circuit. Redux middleware is write-only (actions only). There is no read-intercept. The action-reducer model also means the middleware sees an opaque action, not a typed atom.
Zustand middleware persist, devtools, and immer middlewares wrap the whole store's setState / getState. Structurally very similar. Operates on the entire state object as a unit. There is no per-atom granularity; the handler cannot say "cache only atoms whose name starts with 'user'".
MobX intercept / observe intercept(observable, handler) lets you intercept and cancel mutations on a single observable. Two-sided: you can intercept both get and set. Requires per-observable registration. There is no global stack that covers future observables automatically. Composing multiple interceptors on one observable is possible but not idiomatic.
Apollo InMemoryCache policies Read/write policies on a per-type or per-field basis intercept both cache reads and writes, with readField and toReference helpers. Arguably the most complete prior art for the two-sided intercept idea. GraphQL-specific, deeply coupled to the schema, and not a general-purpose state container.
Jotai atomWithStorage etc. Provides the same end-user capabilities: persistence, reset, validation, undo. Each is a separate atom type. Combining them means nesting wrappers. The behavior is at the atom definition site, not the store site. Swapping environments requires changing atom definitions.
Effector / Effect-TS Strict separation of data (stores/refs) from behavior (effects/events). Philosophically aligned with "atoms as pure identity". A different execution model entirely — reactive event graphs rather than a middleware chain on a key-value store.
Covered elsewhere The middleware chain pattern is well-understood. What is less common is applying it to a keyed atom store with per-atom granularity on both reads and writes. The closest existing art is Apollo's cache policies, but that is GraphQL-specific and not a mental model most React developers reach for.

What they share, and what they do not

Both libraries are reactions to the same observation: Jotai's atom is doing two things at once, and that makes it harder to reuse, test, and reason about. But they carve the problem at different joints.

jotai-branch's novelty is spatial: it asks "where does this write land?" and introduces a store-level boundary that lets the answer be "not yet globally." atoms-alt's novelty is behavioral: it asks "what should happen when a write occurs?" and introduces a chain of handlers that answer that question at runtime rather than at definition time.

Neither replaces the other. A branch is still a store; you could give that branch a handler stack. A handler stack still needs atoms; those atoms could be branched. The ideas compose.

What both ideas share is a preference for environment over definition: the atom should not know whether it lives in a test or in production, whether it will be persisted or discarded, whether it is being edited in a draft or committed. That knowledge belongs to the container.

The atom is a name. Everything else is policy.

Whether that is a good architecture or a leaky one depends on how you think about defaults. If the policy is invisible — configured once at the root, never visible at the use-site — then it is easy to forget it exists. Jotai's wrapping model, for all its awkwardness, makes the policy legible at the definition site. There is a real tradeoff here, and honest prior art on both sides.

Recoil was sunset by Meta in 2023. Its Snapshot API is cited here as prior art because it was the most developed attempt at store-level isolation in the React atom ecosystem, not as an endorsement of its current maintenance status.

Apollo Client's read/write cache policies are documented at apollographql.com/docs/react/caching/cache-field-behavior. They are genuinely underappreciated as a conceptual reference for two-sided interception.

The infinite-render-loop constraint with useSyncExternalStore is not specific to atoms-alt. Any external store that triggers a subscriber from inside a read will hit this. Jotai itself avoids it because atom reads do not trigger subscriptions — subscriptions are registered separately via store.sub.
